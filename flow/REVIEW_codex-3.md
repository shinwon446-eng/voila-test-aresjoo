## 3. 남은 문제, 심각한 순서

### 3.1. 배포 차단: 저장 잔액은 그대로인데 화면은 지급됐다고 말한다

[직접 실행, 화면] 2.3절과 같은 화면에서 예외 대신 지갑 증가 쓰기를 무시했다. 그 순간부터 지갑과 보관함의 읽기도 예외로 막았다. 원본 `getItem`을 별도로 보관해 실제 저장값은 주입을 우회해 읽었다. 이는 2차 4.2의 실패 조합을 보관함 화면으로 확장한 것이다.

| 관찰 대상 | 실제 결과 |
|---|---|
| 저장 상품 | SOLD, soldForUsdt 950 |
| 저장 지갑 | 잔액 10,000, sellback 0건 |
| 머리 잔액 | $10,950 |
| 상세 상태 | USDT로 받음 |
| 상세 금액 | 받은 금액 $950 |

| 상세를 닫고 다시 연 뒤 | USDT로 받음, 받은 금액 $950가 남고 미확정 안내는 사라짐 |

[코드] `claim.ts:22`와 `:24`의 저장이 무시돼도 Zustand 메모리에는 증가한 잔액과 sellback가 남는다. `TakeSheet.tsx:35`의 `useTakeLedger`는 저장된 JSON 판정 결과가 아니라 지갑 메모리 거래 기록을 읽는다. `takeBatch.ts:78`은 SOLD와 메모리의 paid를 보고 taken을 반환하며, SOLD 분기에서는 남아 있는 hold도 무시한다. `InventoryScreen.tsx:85`와 `:150`은 이를 받은 상태와 받은 금액으로 표시한다. `:87`은 상세를 닫을 때 `takeNote`를 지운다.

[판단] 기존 거짓 성공이 함수 응답에서는 사라졌지만 화면에는 남았다. 화면을 다시 열면 경고까지 없어지므로 테스트 사이트에서도 승인할 수 없다. 검증된 장부의 상태와 읽기 실패 상태를 화면에 전달하고, 검증되지 않은 메모리 영수증으로 성공을 확정하지 못하도록 해야 한다. 원본 저장값과의 동기화 없이 hold만 무시하거나 메모리만 신뢰하는 현재 경로가 문제다.

### 3.2. 배포 차단: 정상적으로 받은 옛 자동 받기 상품을 “확인 필요”로 바꾼다

[코드] `takeBatch.ts:65`는 `itemIds`가 없으면 `ref`를 쉼표로 나눠 보관 상품 ID라고 해석한다. 일반 옛 받기는 이 형식과 맞는다. 읽기 전용 `git show c5f85d8:web/lib/claim.ts`와 그 이전 보관함 구현에서 `ref: result.ids.join(",")`를 확인했다.

그러나 옛 자동 받기의 기록은 다르다. `web/components/unboxing/UnboxingRoulette.tsx:348`부터 실제 상품을 `sellOwned`로 팔고 잔액을 올린 뒤 `:351`에서 `ref: 상품종류ID + ":auto"`를 적는다. 보관 상품 ID인 `own_...`는 없다. 이 경로는 `c5f85d8^`와 `3d0a48e`에도 있었다. 현재 접근 가능한 옛 화면이라고 주장하는 것이 아니라 이미 저장됐을 수 있는 정상 기록의 작성 근거다.

[직접 실행] 같은 순서인 `inventory.sell([A],0.95)`, `wallet.creditSplit`, `wallet.addTransaction`을 실제 스토어로 실행하고 ref만 옛 형식으로 남겼다. 상품 참고가 100, 실제 잔액 95, sellback 1건인데 새 판정은 `unconfirmed`, `settleTakeMany`는 `unknown [A]`였다. 실패 주입은 전혀 하지 않았다.

[직접 실행, 화면] 참고가 1,000, soldForUsdt 950, 실제 지갑 10,950, `ref=da-iphone16:auto`인 동일 계약의 옛 기록을 격리 브라우저에 심었다. 상세는 “상태 확인 필요”를 표시하고 “받은 금액”을 숨겼으며 미확정 안내와 지갑 내역 링크를 노출했다. 일반 옛 ref를 쓴 대조군은 “USDT로 받음”, “받은 금액 $950”였다.

[판단] 배포 전 받은 모든 상품이 바뀌는 것은 아니다. 하지만 정상 사용자의 옛 자동 받기 기록은 새 오류 상태로 바뀔 수 있다. “옛 기록은 ref에 ID가 있다”는 가정이 과도하다. 이전 보고서 5.1에서 영수증 없는 SOLD를 일괄 unknown으로 바꾸는 것을 의도한 변화라고 설명한 부분은 이 정상 옛 경로를 놓쳤다. 이번 검수에서 정정한다.

옛 자동 받기의 상품종류 ID는 여러 보관 상품이 공유할 수 있다. 단순히 `:auto`만 지우고 모두 지급 확정으로 인정하는 수정도 안전하지 않다. 연결 근거가 없는 옛 기록을 새 저장 실패와 똑같은 경고로 취급하지 않는 호환 정책과 검증이 필요하다. 이번에는 그 정책을 임의로 구현하지 않았다.

### 3.3. 높음: 확인 대기 키가 미지급 상품을 계속 격리하고 복구 경로가 없다

[직접 실행] 시작 상품 A는 참고가 100, IN_STORAGE, 잔액 0이다. 모든 재시도는 주입을 제거하고 두 스토어를 다시 읽은 뒤 같은 ID로 했다.

| 주입 조건 | 첫 응답 | 저장 상품, 잔액, sellback | 표시 | 장애 제거 뒤 |
|---|---|---|---|
| 표시 쓰기 성공, 보관함 SOLD 쓰기 예외, 표시 삭제 무시 | unknown [A] | IN_STORAGE, 0, 0건 | A 남음 | 반복 호출과 단일 settleTake 모두 unknown, 잔액 0 |
| 표시 쓰기 성공, 보관함 SOLD 쓰기 예외, 이후 장부 읽기까지 예외 | unknown [A] | IN_STORAGE, 0, 0건 | A 남음 | 재수화해도 unknown, 받을 수 있는 목록에서 제외 |
| 보관함 SOLD 쓰기 실패 사이에 다른 작성자가 충전 50과 그 내역 저장 | unknown [A] | IN_STORAGE, 50, sellback 0건, deposit_usdt 1건 | A 남음 | 충전 기록이 있어도 계속 unknown, 상품 지급 0 |
| 대조군: 표시 뒤 보관함과 지갑 쓰기 모두 무시하되 읽기와 표시 삭제는 가능 | failed, left [A] | IN_STORAGE, 0, 0건 | 지워짐 | settled 95, 최종 SOLD, 잔액 95, sellback 1건 |
| 대조군: 지급 정상, 표시 삭제만 실패 | settled, taken [A:95] | SOLD, 95, 1건 | A 남음 | already 95, 추가 지급 0, 표시 삭제됨 |

[코드] `takeBatch.ts:79`는 보관 중인 상품에 표시가 있으면 무조건 unconfirmed로 분류한다. 다음 호출은 `:273`에서 unknown으로 보내므로 `:303`의 깨끗한 미지급 재판정까지 가지 못한다. `:278`과 `:317`의 정리는 이미 지급된 것으로 확인된 상품만 구제한다. 표시에는 시작 전 잔액이나 실패 단계가 없고 ID만 있다. 보관 중인 미지급 상품을 안전하게 재판정할 복구 자료와 사용자 경로가 없다.

[코드] 충전이 겹친 경우 `:307`부터 전체 잔액 증가에서 이번에 SOLD가 된 상품 금액만 설명된 증가로 인정한다. 다른 입금 내역의 50은 빼지 않는다. `walletStore.ts:176`의 `settleDeposit`와 `lib/depositCredit.ts:19` 호출에는 이 받기의 Web Lock이 없다.

[직접 실행의 한계] 충전 겹침 표의 실행은 첫 장부 읽기와 사후 판정 사이에 Map의 저장 지갑을 다른 작성자가 바꾼 것으로 주입했다. 두 실제 Chrome 탭의 충전과 저장 실패를 함께 실행하려던 후속 시도는 기존 3002 서버가 `ERR_CONNECTION_REFUSED`를 반환해 시작하지 못했다. 서버를 새로 띄우지 않았다. 따라서 실제 두 탭의 충전 타이밍 재현을 완료했다고 주장하지 않는다. 계정 변경 시험의 두 탭 Web Lock 실행은 그 전에 완료했다.

[추정] 표시만 저장한 뒤 탭이 종료돼 정리 단계가 실행되지 않아도 같은 IN_STORAGE, 표시 있음 상태가 남는다. 탭 강제 종료 자체는 실행하지 않았다.

[판단] 격리가 중복 지급보다 안전한 것은 맞다. 따라서 표시를 시간만 보고 지우거나 재지급하면 안 된다. 다만 지금은 실제로 돈이 전혀 들어오지 않은 정상 보관 상품도 장애가 해소된 뒤 계속 받을 수 없다. 보관함과 지갑 내역 링크에는 이를 끝낼 수 있는 복구 동작이 없다. 3.1과 3.2를 고쳐도 이 미지급 복구 제한을 해결하거나 명시적으로 처리할 수단이 필요하다.

## 4. 가장 중요한 옛 기록 호환성의 최종 표

[직접 실행] 모든 행은 별도 자료로 시작했고 새 함수 호출 뒤 저장 잔액이 추가로 늘지 않는지 확인했다. 화면 열은 실제 브라우저에서 실행한 것만 적었다.

| 정상 과거 기록 | 새 함수 응답 | 저장값 | 실제 상세 화면 | 판정 |
|---|---|---|---|---|
| 일반 받기, itemIds 없음, ref에 보관 상품 ID | settled, already [A:95], 새 금액 0 | SOLD, 잔액 95, 기존 sellback 1건 | 1,000 대조 자료에서 USDT로 받음, 받은 금액 $950 | 호환됨 |
| 옛 자동 받기, itemIds 없음, ref가 상품종류ID:auto | unknown [A], 새 금액 0 | SOLD, 잔액 95, 기존 sellback 1건 | 확인 필요, 받은 금액 없음 | 정상 기록 오판 |
| 옛 현금 결과, 상품별 ID 없는 box:cashback x1 | settled, already, 새 금액 0 | SOLD, soldForUsdt와 valueUsdt가 같음, 잔액 유지 | 제거된 상품을 모사한 1,000 자료에서 USDT로 받음, 받은 금액 $1,000 | 실행한 조건은 호환됨 |
| 실제 옛 형식 dollar-apple / wave-cashback-50 | settled, already 0.5, 새 금액 0 | sell([A],1)과 creditSplit으로 저장한 SOLD, 잔액 0.5, cashback 내역 1건 | 이 정확한 ID의 브라우저 재실행은 안 함 | 함수 호환됨 |
| 실물 SOLD, itemIds와 보관 상품 ref 모두 없는 자료 | unknown [A] | SOLD, 잔액 95, 내역 1건 | 이 임의 형식의 별도 화면 실행은 안 함 | 모든 무ID 기록을 구제하는 것은 아님 |

[코드] 옛 현금 결과는 `takeBatch.ts:71`이 예외로 다룬다. 현재 상품을 찾으면 cash 종류인지 보고, 못 찾으면 `soldForUsdt === valueUsdt`를 본다. 과거 `opening.ts`는 현금 결과를 `inventory.sell(cash,1)`로 지급하고 `ref=box:cashback xN`을 남겼다. `c5f85d8`의 상품 구성에는 dollar-apple 가격 1의 `wave-cashback-50` 생성 근거도 있다.

[추정] 과거 현금 상품의 ID가 현재 다른 종류의 상품에 재사용됐으면 100% 지급 기록이어도 현재 종류가 우선해 오판할 수 있다. 임의의 현금 지급값과 현행 실물 ID 조합에서는 함수가 unknown을 반환했지만, 실제 과거와 현재 카탈로그에서 그런 ID 재사용을 확인한 것은 아니다. 이 조건을 확정 결함이나 배포 차단 건수로 더하지 않았다.

[판단] 질문의 답은 “옛 상품 전부가 확인 필요로 바뀌지는 않지만, 정상 옛 자동 받기 상품은 바뀐다”이다. 기존 `takeFault.test.ts:227`의 옛 기록 시험은 ref에 보관 상품 ID가 있는 경우만 검사한다. `:393`의 현금 예외 시험 역시 옛 자동 받기 계약을 덮지 못한다.

## 5. 한 탭의 실행 순서와 제공 화면

[직접 실행] 저장 가능한 Map을 붙인 실제 스토어에서 A, B, C 각 100으로 시작했다. `settleTakeMany([A,B])`, `settleTakeMany([B,C])`, `settleTake(A)`를 `Promise.all`로 동시에 호출했다.

| 호출 | 응답 |
|---|---|
| [A,B] | settled, taken A:95와 B:95, amountUsdt 190 |
| [B,C] | settled, already B:95, taken C:95, amountUsdt 95 |
| 단일 A | settled 95, already true |
| 저장 결과 | 모두 SOLD, 잔액 285, sellback 2건, 표시 키 없음 |

[판단] 한 탭에서 겹치는 받기 요청을 차례로 실행하는 수정은 이 재현을 통과했다. 이 큐가 별도 충전 쓰기까지 직렬화한다는 뜻은 아니다.

[화면] melt7의 `h7-recovered-results.png`는 불일치 상품 두 개에 확인 필요가 붙고 잔액 반영은 0이다. `h4`와 `h10`은 상세와 선택 목록의 격리를 보여 준다. melt8의 `one-4-taken-mobile.png`는 정상 수령 $7.59, `five-3-take-sheet-desktop.png`는 5개 합계 $39.85의 정상 흐름이다. 제공 화면은 저장 실패 후 메모리만 성공으로 남는 3.1이나 옛 자동 받기의 호환성을 입증하는 자료가 아니다.
