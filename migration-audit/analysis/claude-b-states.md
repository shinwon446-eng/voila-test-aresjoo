# 상태 전이 명세 (Claude 분석가 B)

기준 커밋 `63445c7` 의 소스를 읽고, 배포된 참조 사이트를 Playwright 로 실제로 눌러 확인한 결과다. 분석만 했다. `web/` 과 기존 문서는 고치지 않았다. 인터랙션마다의 핸들러와 줄 번호는 같은 폴더의 `claude-b-interactions.md` 에 있다. 이 문서는 기능마다 "어떤 상태에서 무엇을 하면 무엇이 어떻게 바뀌는가"를 사례로 적는다. 단추 하나에 결과가 여럿이면 사례도 여럿이다.

## 0. 읽는 법

- 확인의 말: **실행 NN:id** 는 `migration-audit/harness/claude-b/NN-*.mjs` 의 그 시나리오를 직접 돌려 본 것이다(명령은 `claude-b-interactions.md` 0.2 절의 표). **화면** 은 그 실행에서 화면의 글을 읽은 것, **코드** 는 소스에서만 읽은 것, **짐작** 은 근거 없이 미룬 것이다. 실행하지 않은 것을 확인했다고 적지 않았다.
- 저장 키의 줄임말(W 지갑, I 보관함, J 개봉 기록장, F 추첨 값과 회차, S 설정, C 통화, R 후기, A 계정 목록, SS 세션, M 확인 대기 표시, L 고른 언어)은 `claude-b-interactions.md` 0.4 절과 같다. 실제 키 앞에는 `voila-test-aresjoo:` 가 붙는다.
- 기존 시험: `web/tests/*.test.ts` 는 화면 없이 도는 단위 시험이다. `web/scripts/capture/*.mjs` 는 개발 서버(`localhost:3002`)의 화면을 누르는 검수 스크립트다(배포 사이트를 대상으로 돌린 기록은 찾지 못했다). 둘 다 없으면 "없음"이라고 적는다. 시험 파일의 제목을 읽고 대응시킨 것이며, 시험을 이번에 다시 돌리지는 않았다.
- 이 사이트의 계정과 장부는 전부 이 브라우저 안의 시험 장부다(`lib/account.ts:47-48`, `lib/browserAccount.ts:78-79`). 메일을 보내지 않고 밖으로 나가는 요청이 없다.

화면이 따르는 개봉 상태 기계(`lib/openingFlow.ts:99-130`)의 상태 이름을 그대로 쓴다: READY, CONFIRMING, PURCHASE_PROCESSING, OUTCOME_COMMITTED, OPENING, REVEALED, SETTLING, SETTLED, INSUFFICIENT_BALANCE, PURCHASE_FAILED, SETTLEMENT_PENDING, SETTLEMENT_FAILED, RECOVERY_REQUIRED.

## 11. 중요한 것만 다시

1. 장부는 연출보다 먼저 적힌다(CL-S-023). 연출 중에 새로 고치거나, 뒤로 가거나, 탭을 바꾸거나, 다시 눌러도 구매는 정확히 한 번이고 결과는 같은 것으로 다시 나온다(CL-S-036, 039, 040, 041, 043, 045). 잃거나 겹친 사례는 찾지 못했다.
2. 받기도 한 번만 지급된다(CL-S-051, 061, 071). 저장이 실패하면 받지 못했다고 말하고 화면의 장부를 저장된 장부에 다시 맞춘다(CL-S-064, 065).
3. 다만 모바일 폭에서는 받기의 확인창을 같은 자리의 두 번 누름으로 건너뛸 수 있다(CL-S-058, 088). 돈은 한 번만 움직이지만 되돌릴 수 없는 행동이 확인 없이 된다.
4. 지갑 내역에는 박스 열기와 받기 거래가 나오지 않는다(CL-S-067 의 "걸리는 것").
5. 두 저장 키(지갑과 보관함)를 한 번에 묶지 못한다는 한계는 소스가 스스로 적고 있다(`takeBatch.ts:39-41`). 구매 쪽(`opening.ts:66-110`)도 같은 구조다: 차감, 기록 추가, USDT 결과 반영, 거래 기록이 저장소 쓰기 여러 번으로 나뉜다. 쓰는 도중에 탭이 죽는 경우를 구매에 대해 보는 시험은 찾지 못했다(받기에 대해서는 `tests/takeFault.test.ts` 가 본다). 이것은 소스를 읽고 적은 것이고 재현하지는 않았다.
