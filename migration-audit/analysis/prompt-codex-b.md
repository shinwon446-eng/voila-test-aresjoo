적을 것

1. 카탈로그의 지문. web/lib/products.ts 와 web/lib/catalog2 에서 실제로 화면에 쓰이는 자료를 직접 불러(`npx tsx` 로) 다음을 세고 해시를 내라: 박스 수, 박스마다의 구성품 수, 상품 수(고유), 사진이 있는 상품 수, 가격의 분포, 카테고리, 세 언어 이름이 빠진 것, 박스마다 확률의 합(정확히 얼마인지), 확률표의 순서 규칙. 박스 전체의 (slug, 가격, 상품 id, 확률) 을 정해진 순서로 이어 붙인 SHA-256 을 적어라. 이 해시가 뒤의 모든 변경에서 같아야 한다. 재는 스크립트의 내용을 보고서에 그대로 붙여라(다른 사람이 다시 돌릴 수 있게).

2. 화면에 보이는 확률과 실제 추첨이 같은 원천을 쓰는가. 박스 화면의 확률 요약, 상품별 표, 결과 화면의 "나올 확률", 검증의 다시 계산이 각각 어디서 수를 가져오는지 따라가라. 반올림과 자릿수가 다른 자리.

3. 추첨. web/lib/fairness*.ts, web/lib/opening.ts, web/stores/fairStore.ts, web/server/rng.ts: 시드, 회차, 해시에서 수를 만드는 식, 수에서 상품을 고르는 식, 여러 개를 열 때의 회차, 무료 열기, 보장 규칙이나 게이지가 있다면 그 식. 정해진 시드로 열 번을 직접 돌려 (회차, 나온 수, 상품 id) 표를 적어라. 이 표가 회귀 테스트의 기준값이 된다.

4. 돈. 박스 값의 차감(출처 배분 포함), USDT 로 받기(web/lib/takeBatch.ts, claim.ts, types.ts 의 REFUND_RATE), 충전, 출금(수수료, 최소액, 출금 가능한 잔액), 통화 환산과 표기(web/lib/useCurrency.ts 등), 반올림 규칙. 식마다 파일과 줄. 경계값 사례를 직접 계산해 표로(예: 받을 금액이 0.005 에서 갈리는 값, 카드 충전분과 크립토 충전분이 섞인 잔액).

5. 영속성. 저장 키 전부, 값의 모양, 새로고침 뒤 복원되는 것과 사라지는 것, 저장 실패(용량 초과)일 때의 동작, 두 탭. 알고 있는 사실 하나: 개봉 한 건이 확률표를 통째로 저장해(fair.dropTable) 800번쯤 열면 저장 한도가 찬다. 이것을 직접 재서 확인하고, 이번 감사의 범위(원본과 같게)에서는 "알려진 기존 결함"으로 분류해 적어라. 고치자고 하지 마라.

6. 인증과 API. 서버가 없는 정적 배포에서 가입, 로그인, 세션이 어떻게 흉내 내지는가(web/lib/account.ts, browserAccount.ts, communityReviewApi.ts 등). NEXT_PUBLIC_API_BASE 가 비어 있을 때와 있을 때의 갈림. 서버가 있어야만 되는 기능의 목록(배송 접수 등)과 지금 화면에서 그것이 어떻게 보이는가.

7. 후기와 신뢰 자료. 후기가 어디서 오는가(web/lib/reviewSamples.ts 의 예시 28건, publishedReviewExamples.ts, 내가 쓴 후기), 예시와 실제가 화면에서 구분되는가, 별점 요약의 식, 나온 상품(web/lib/wins.ts)과 검증 기록의 원천. 새로 지어내지 말고 지금 있는 것을 분류만 하라.

8. 백로그의 분류. 루트의 STATE.md, RELEASE-READINESS.md, DECISION_LOG.md, IMPROVEMENT_LOOP.md, opening/STATE.md, flow/MELT_SPEC.md 에 적힌 기능과 계획을 표로: 구현 완료, 부분 구현, 화면만 있음, 서버 미연결, 계획만 있음, 폐기됨, 지금 닿지 않음. 근거(코드 위치나 문서 줄)와 함께. 문서가 코드와 어긋나는 자리를 따로.

9. 회귀 테스트가 지켜야 하는데 지금 없는 것. 위 1에서 7까지의 값 가운데 web/tests 가 이미 고정하고 있는 것과 아닌 것.
